# Approval envelope v2 — development increment 2

Synthetic PAY-104 lab profile, not a release or a production authorization mechanism. The signed v1.0.0 archive and existing AMGB corpus are untouched.

## Contract

The `itm-local-approval-v2` envelope signs canonical JSON prefixed with `ITM-LOCAL-APPROVAL-V2` and a NUL byte. It carries a fixed lab audience, actor, author, policy role, Ed25519 public-key fingerprint, exact candidate binding (head, base, spec, policy, harness and path semantics), 128-bit request nonce, issue time and expiry. Validity is `issued_at <= evaluated_at < expires_at`, with a maximum 300-second lifetime. Verification requires the expected request context, not a nonce or evaluation time supplied by the envelope. A shared public key cannot satisfy multiple registered actors, including the author's registered key if available. Repeated envelopes cannot fill another role. This does not establish organizational independence.

Fresh `evaluate_policy` calls require a valid `approval_context`. The fixture runner generates a random challenge and uses its local clock; the context is recorded for deterministic historical replay. Historical v1 and increment-1 evidence replay under their original profiles; only historical fnmatch-v1 replay accepts legacy HMAC. The legacy signing helper remains for compatibility tests. `_historical_semantics` and the pure `evaluate_decision` (which accepts already verified actors) are internal replay/evaluation mechanisms, not current authorization interfaces. Counterfactual replay reuses historical identities hypothetically.

## Limits

The verifier is stateless. Reuse within the same challenge and time window remains possible. Trusted callers must supply the expected context and current time; clock rollback, crash recovery, challenge consumption, durable revocation and atomic merge enforcement remain unqualified. Historical replay does not establish current validity. Synthetic keys, trust and anchors are still generated by the local runner. The same-user lab demonstrates internally consistent evidence, not organizational authority. External GitHub control receipts and changeset approvals are unchanged. No hostile-code isolation or merge-queue enforcement is established.
